2. PostgreSQL Installation and System Integration
2.1 Installation Verification

PostgreSQL version 18.3 was installed on the local machine. Installation was verified using the following command:

psql --version

Output:

psql (PostgreSQL) 18.3

This confirms:

The PostgreSQL client (psql) is correctly installed.

The system can execute PostgreSQL command-line utilities.

The installed version is recognized globally.

2.2 System PATH Configuration

The PostgreSQL binary directory was manually added to the Windows System Environment Path variable:

C:\Program Files\PostgreSQL\18\bin
Purpose of PATH Configuration

Without adding PostgreSQL to the system PATH:

Windows cannot locate psql.exe.

Command-line database interaction fails.

Automation scripts referencing PostgreSQL utilities would fail.

Adding the directory to PATH enables global execution of PostgreSQL tools from any terminal session.

3. Server Authentication and Connectivity Verification

Connection to the PostgreSQL server was established using:

psql -U postgres

This command performs the following operations internally:

Initiates a TCP connection to localhost on port 5432.

Applies authentication rules defined in pg_hba.conf.

Validates password credentials.

Establishes a session bound to the postgres database.

Successful connection confirms:

PostgreSQL server service is running.

Authentication mechanisms are functional.

Superuser access is operational.

Local database connectivity is verified.

4. Project Database Creation

A dedicated database for the application was created:

CREATE DATABASE payfusion;
4.1 Rationale for Dedicated Database

Using a separate database ensures:

Logical data isolation.

Independent backup management.

Independent migration control.

Prevention of cross-project interference.

Clean deployment lifecycle management.

Using the default postgres administrative database for application data is considered poor architectural practice.

5. Role-Based Security Architecture
5.1 Security Design Principle

The system follows the Principle of Least Privilege, which states:

A system component should possess only the minimum permissions required to perform its intended function.

Under this model, the application must not connect using a superuser account.

5.2 Creation of Restricted Application Role

A dedicated application role was created:

CREATE ROLE payfusion_user WITH LOGIN PASSWORD 'StrongPassword';
Technical Explanation

CREATE ROLE creates a new PostgreSQL role.

WITH LOGIN enables authentication capability.

PASSWORD stores a securely hashed credential in the system catalog.

This role:

Is NOT a superuser.

Cannot create databases.

Cannot create roles.

Cannot bypass row-level security.

Has no initial privileges.

This ensures strict operational boundaries.

6. Controlled Permission Assignment
6.1 Grant Database Connection Privilege
GRANT CONNECT ON DATABASE payfusion TO payfusion_user;

This allows the role to authenticate into the payfusion database, but does not permit schema modification.

6.2 Switch Database Context
\c payfusion

All subsequent privilege configurations apply within the payfusion database.

6.3 Grant Schema-Level Permissions
GRANT USAGE ON SCHEMA public TO payfusion_user;
GRANT CREATE ON SCHEMA public TO payfusion_user;
Explanation

USAGE allows access to objects within the schema.

CREATE allows creation of tables, indexes, and related objects.

Without these privileges, Django migrations would fail during table creation.

6.4 Configure Default Object Privileges
ALTER DEFAULT PRIVILEGES IN SCHEMA public
GRANT ALL ON TABLES TO payfusion_user;

ALTER DEFAULT PRIVILEGES IN SCHEMA public
GRANT ALL ON SEQUENCES TO payfusion_user;
Importance of This Step

PostgreSQL treats:

Tables

Sequences (used for auto-increment fields)

as separate entities.

Django relies on sequences for automatic primary key generation (AutoField).

Without granting privileges on sequences:

INSERT operations would fail.

Primary key generation would be blocked.

This configuration ensures full CRUD capability within the database while maintaining restricted global privileges.

7. Role Verification

Roles were verified using:

\du

Result:

Role name        | Attributes
-----------------+-----------------------------------------
payfusion_user   |
postgres         | Superuser, Create role, Create DB, Replication, Bypass RLS

This confirms:

payfusion_user has no elevated privileges.

postgres retains administrative authority.

Security boundaries are properly enforced.

8. Final Architecture After Phase 0

The database system is structured as follows:

PostgreSQL Server
│
├── Database: payfusion
│ └── Schema: public
│
├── Role: postgres (Superuser – administrative only)
└── Role: payfusion_user (Restricted application role)

9. Security Model Outcome

If the application layer is compromised:

Potential impact is limited to:

Tables inside the payfusion database.

The attacker cannot:

Drop other databases.

Create new roles.

Escalate privileges.

Modify PostgreSQL system catalogs.

Access administrative functions.

This containment strategy aligns with production-grade backend architecture standards.
