PHASE 2 — CUSTOM AUTHENTICATION SYSTEM IMPLEMENTATION
Project: PayFusion
Framework: Django
Database: PostgreSQL

PHASE OBJECTIVE

The objective of Phase 2 was to replace Django’s default authentication system with a fully controlled custom user model.

Django provides a default user model (auth.User), but using it directly in production projects is discouraged because it becomes extremely difficult to modify later once migrations have been applied and the system is in use.

Therefore, we implemented a custom user model at the beginning of the project to ensure:

• Future extensibility
• Full control over authentication fields
• Clean database architecture
• Compatibility with multi-tenant design
• Ability to add roles, permissions, or tenant relations later
• Avoidance of migration conflicts in the future

This is considered a best practice for professional Django projects.

ARCHITECTURAL DECISION

Three possible approaches exist when implementing authentication in Django.

Option 1 — Use Django’s default auth.User
This option was rejected because extending the default user model later is extremely difficult and can require database reconstruction.

Option 2 — Create a fully custom user using AbstractBaseUser
This option provides maximum flexibility but requires rebuilding the entire authentication system manually (permissions, admin, password management, etc.), which adds unnecessary complexity.

Option 3 — Extend Django’s AbstractUser
This option was selected.

AbstractUser inherits Django’s complete authentication system while allowing developers to extend it safely.

Advantages include:

• Built-in password hashing
• Built-in authentication backend support
• Built-in admin integration
• Built-in permissions and groups
• Easy addition of future fields

CREATION OF THE USERS APPLICATION

A dedicated application was created to handle authentication and user management.

Command used:

python manage.py startapp users

Purpose of this separation:

• Keeps authentication logic isolated
• Improves project maintainability
• Enables future expansion such as profiles, roles, or permissions
• Supports modular architecture

CUSTOM USER MODEL IMPLEMENTATION

Inside users/models.py, a new User model was created by extending Django’s AbstractUser.

The implementation was intentionally minimal for Phase 2 because the main objective was to replace Django’s default user model structure.

The model currently inherits all default Django authentication fields including:

• username
• password
• email
• first_name
• last_name
• is_active
• is_staff
• is_superuser
• date_joined
• last_login

Additional fields will be added in later phases when implementing platform features.

ACTIVATING THE CUSTOM USER MODEL

Django must be explicitly told to use the custom user model instead of the default one.

This was done by modifying the project settings file.

In settings.py the following configuration was added:

AUTH_USER_MODEL = "users.User"

This setting instructs Django to use the User model defined in the users application for all authentication operations.

Important rule:

This setting must be defined before the first migrations are applied.
Changing it later can cause severe database conflicts.

MIGRATION RESET AND CLEAN INITIALIZATION

During development an initial migration conflict occurred because migrations were created before the custom user model was properly configured.

To resolve this, the project database was reset and migrations were regenerated from a clean state.

Steps performed included:

• Removing existing migration files
• Resetting the database schema
• Recreating migrations from scratch
• Running migrations again with the corrected configuration

This ensured that the authentication system was initialized properly with the custom user model from the start.

POSTGRESQL PERMISSION ISSUE AND RESOLUTION

While running migrations, a database error occurred.

Error message:

permission denied for schema public

Cause of the issue:

The PostgreSQL database user created for the application (payfusion_user) did not have sufficient privileges to create tables inside the public schema.

Although the user owned the database, PostgreSQL requires explicit schema-level permissions for table creation.

The following permissions were granted to resolve the issue:

GRANT USAGE ON SCHEMA public TO payfusion_user;

GRANT CREATE ON SCHEMA public TO payfusion_user;

ALTER DEFAULT PRIVILEGES IN SCHEMA public
GRANT ALL ON TABLES TO payfusion_user;

ALTER DEFAULT PRIVILEGES IN SCHEMA public
GRANT ALL ON SEQUENCES TO payfusion_user;

After applying these permissions, migrations executed successfully.

REGISTERING THE CUSTOM USER MODEL IN ADMIN

Django automatically registers the default auth.User model in the admin panel.
However, when using a custom user model, it must be manually registered.

Inside users/admin.py the custom User model was registered using Django’s built-in UserAdmin class.

This allows the admin panel to provide the same interface used for managing users in the default Django system.

After registration, the Django admin interface correctly displayed:

• Users
• Groups

DATABASE VERIFICATION

After migrations were completed, the database tables were inspected using Django’s database shell.

Command used:

python manage.py dbshell

Then:

\dt

Expected result:

The default auth_user table should NOT exist.

Instead, the system should contain a users_user table representing the custom user model.

Verification confirmed that:

• users_user table exists
• auth_user table does not exist
• authentication tables are correctly linked

This confirms the custom authentication system is functioning correctly.

SECURITY CONSIDERATIONS

The project database was configured using a dedicated application user instead of the PostgreSQL superuser.

This follows the security principle known as "least privilege".

The application user has only the permissions required to:

• connect to the database
• create tables during migrations
• read and write application data

Administrative database operations remain restricted to the postgres superuser.

SYSTEM STATE AFTER PHASE 2

At the completion of Phase 2, the PayFusion backend system has:

• A fully operational custom authentication system
• A clean migration history
• A properly configured PostgreSQL database
• A functional Django admin interface
• A verified custom user table

The authentication architecture is now stable and ready for integration with the platform’s multi-tenant system in future phases.
